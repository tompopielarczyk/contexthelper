# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Loading the extension

There is no build step. Load the extension directly in Chrome:
1. Go to `chrome://extensions/`
2. Enable "Developer mode"
3. Click "Load unpacked" → select this directory
4. After any code change: click the reload button on the extension card (for content script changes, also refresh the target page)

## Architecture

**Chrome MV3 extension** — vanilla JS, no bundler, no dependencies.

```
background.js          # Service worker: context menu + AI calls
content.js             # IIFE injected into every page: overlay UI
options.html/js/css    # Settings page
lib/
  api-client.js        # Provider fetch wrappers, streaming (SSE), error mapping
  storage.js           # chrome.storage abstraction, default actions/settings
  chat.js              # Pure run helpers: streaming decision, LLM config pick, throttle, retry/refine/ask helpers
  model-list.js        # Pure model-list helpers: unknown-model warning rule, cache key, API key fingerprint
  prompt.js            # Pure action-template rendering and page-context windowing
  page-probe.js        # probeSelection: the one self-contained function injected to read the selection
  webhook.js           # Webhook delivery, payload templates, per-origin permissions
```

Supported providers: Anthropic, OpenAI, Google Gemini, OpenRouter (includes open-source models), DeepL, and `custom` (any OpenAI-compatible endpoint: Ollama, LM Studio, vLLM). Each provider has its own `callXxx()` function in `api-client.js`; OpenAI, OpenRouter and custom share `callChatCompletions`. The model field is a free-text combobox (`<input>` + `<datalist>`) — any model ID can be typed directly (no "Other..." special case; see Model lists below).

### Data flow

1. User selects text → right-clicks → picks action from "ContextHelper" submenu, **or** presses a keyboard shortcut (see Keyboard shortcuts below)
2. `background.js` (`handleMenuClick` or `handleCommand`, both thin adapters over the shared `runAction`) builds a request and hands it to `runChat`, which sends `AI_PROCESSING_START` and calls `lib/api-client.js`
3. Content script shows loading spinner (Shadow DOM overlay)
4. For tooltip results the answer streams in (`AI_CHUNK`); the background then sends `AI_RESULT` or `AI_ERROR`
5. Content script either replaces selected text or shows result tooltip (with the refine controls)

### The `runChat` runner

Every AI run (actions, refine, Ask, retries) goes through `runChat(tab, settings, buildRequest, retrySpec, clientId)` in `background.js`:
- **Request ids** are `crypto.randomUUID()` (content-side comparisons survive a worker restart). `_abortControllersByTab` keeps one `{ controller, requestId }` per tab; a new run aborts the previous one, and so do `showTabNotice` and `ASK_PROMPT` (all through `abortTabRun(tabId)`). A run's `finally` deletes the entry only while it still holds its own controller, so an older run never removes a newer run's entry.
- `buildRequest()` runs **after** `AI_PROCESSING_START`, so its throws (missing model/key, deleted action, DeepL refine) surface as `AI_ERROR` through the requestId gating. `signal.aborted` is re-checked after every await.
- **Streaming** only when `shouldStream({ provider, displayMode, editable })`: not DeepL, and the result goes to a tooltip (`tooltip`, or `auto` on a non-editable selection). Insert paths stay atomic behind the spinner. Chunks are throttled to `CHUNK_THROTTLE_MS` (100 ms) and carry only the unsent text: `nextChunk(sentLength, text)` (`lib/chat.js`) gives `{ offset, delta }`, empty deltas are skipped. The content script appends a delta only when `offset === streamShownLength`; any mismatch marks the stream desynced (later chunks of that run are ignored) and the run waits for `AI_RESULT`, which always carries the full text. Deltas render as a fading `.cmn-fade` span that turns back into plain text on `animationend` (`renderStreamDelta`; no animation under `prefers-reduced-motion`). The throttle is **cancelled, never flushed**, before `AI_RESULT` and `AI_ERROR` — a fast answer goes straight from the spinner to the result, without flashing the streaming tooltip.
- **Ordered sends** — every tab message of a run (START, chunks, heartbeats, `AI_RESULT` / `AI_ERROR`) goes through one per-run promise chain (`send` in `runChat`), so a chunk can never overtake the terminal message.
- **Stream rules** (`readStream` in `api-client.js`): inactivity in two phases, both reset by any bytes (keep-alives, pings, role or reasoning chunks) — `preAnswerIdleMs` 90 s until the first answer text (reasoning models think silently), then `idleMs` 30 s → "API stream stalled"; `totalMs` 240 s bounds both → "API response took too long". Reasoning output is never answer text: Anthropic `thinking_delta` / `signature_delta` / `ping`, Gemini parts with `thought: true` (also in `extractGeminiText`); EOF without a terminal event → "stream ended unexpectedly" (even after partial text). Terminal events: Anthropic `message_stop`, chat completions `finish_reason` or `data: [DONE]`, Gemini `finishReason` (any value, incl. `CONTINUATION`, which keeps the text so far). The raw stop reason (Anthropic `message_delta.delta.stop_reason` — collected, never terminal; chat `finish_reason`; Gemini `finishReason` / `promptFeedback.blockReason`) classifies an empty answer once the stream has ended (see Reasoning models); OpenRouter's `: OPENROUTER PROCESSING` comments are skipped and its trailing usage chunk is never read (the first `finish_reason` ends the read). Mid-stream provider errors (Anthropic `event: error`, OpenRouter HTTP-200 chunks with `error`) reject. `readStream` owns its own abort listener and idle/total timers, because for streaming calls `fetchWithErrorHandling` returns (and drops its listener) once headers arrive.
- **Keepalive + heartbeat** — from START until the run ends, every `KEEPALIVE_INTERVAL_MS` (20 s) `chrome.runtime.getPlatformInfo()` resets the worker's idle timer and `AI_HEARTBEAT { requestId }` (through the ordered `send` chain) tells the page the run is alive — reasoning models can think for minutes without a chunk. `stopHeartbeat()` clears the interval and sets the run's `ended` flag **before** `AI_RESULT` / `AI_ERROR` is enqueued (and again in `finally`); a heartbeat already queued in the chain re-checks `ended` / `signal.aborted` and becomes a no-op, so a heartbeat never follows the terminal message. Test streaming with DevTools closed (an open inspector keeps the worker alive and hides lifetime bugs).
- **Retry** — `AI_ERROR` carries `partialText` and `retry` (a `RetrySpec`) only when `isRetryableError(err)`: `APIError` with status 0 (network, timeout, stall, stream error), 429 or ≥ 500, unless it carries `retryable: false` (the deterministic empty answers: budget spent on reasoning, refusal — see Reasoning models). Config errors from `buildRequest` get `retry: null`. The error tooltip then shows `↻ Retry` (no 6 s auto-dismiss) and sends `RETRY_RUN`; `handleRetryRun` dispatches on `retry.kind`: `'action'` (`actionId`, `selectionText`, `editable`, `pageVars`), `'refine'`, `'ask'`. The Retry button's `mousedown` calls `preventDefault()` so an insert-mode retry can still replace the original selection.
- **Early spinner (`clientId`)** — runs started from the page (refine, Ask, Retry) show the spinner immediately and carry a `clientId`; `runChat` and `showTabNotice` echo it in `AI_PROCESSING_START`. Dismissing the spinner before START records the id in `dismissedClientIds`, and a later START with that id is answered with `CANCEL_ACTION`. A START with a different id marks the pending one dismissed. Every background early return for such a request must answer through `showTabNotice(..., clientId)`; the start watchdog below is only the safety net.
- **Watchdogs (content.js)** — module-level timers, deliberately not in `activeCleanups` (the first chunk's `hideOverlay()` would clear them). Neither ever resends.
  - *Start* (`START_WATCHDOG_MS`, 20 s): armed by `requestRun`; cleared by any START, by dismissal (`cancelActiveRun`), by a newer `requestRun` and by the send-failure path. On expiry, while the id is still pending: error tooltip `'The request did not start — try again'`, and the id is marked dismissed, so a very late START only cancels the run.
  - *Liveness* (`LIVENESS_TIMEOUT_MS`, 60 s = three missed heartbeats): armed by every START, reset by every `AI_HEARTBEAT` and `AI_CHUNK` of the active run, cleared by its `AI_RESULT` / `AI_ERROR` / cancellation. There is no overall deadline — the API-side limits (90 s to headers, stream inactivity, 240 s total, at most one 400 retry per tuning field) end a run, and the page gives up only when the worker went silent (died). On expiry: `CANCEL_ACTION { requestId }` (`sendCancel`, so the background stops spending tokens), `activeRequestId = null` (late messages are dropped) and error tooltip `'No response — the request may have been interrupted'`.
- **Cancellation UX** — the spinner and the streaming tooltip cancel only on Esc or ✕ (`cancelActiveRun` → `CANCEL_ACTION`); a click outside them does nothing, so clicking back into the page (e.g. the textarea an insert run will write to) never throws away a paid request. Finished result tooltips still close on an outside click. Insert safety does not depend on this: `replaceSelectedText` / `forceReplaceInDOM` write only while `snapshotStillSelected` (same element/offsets/substring, or the same DOM range and text) holds.
- **API key check** — `missingApiKeyError(config)` in `lib/chat.js` is shared by actions, refine and Ask; `custom` configs may be keyless.

### Message protocol (background ↔ content script)

Background → content (`chrome.tabs.sendMessage`):
- `AI_PROCESSING_START` — `requestId`, `clientId?`, `tooltipSettings`; content script shows spinner
- `AI_CHUNK` — `requestId`, `offset`, `delta`, `tooltipSettings`; streaming tooltip (plain text, caret). `delta` is only the new text, starting at `offset` chars into the answer
- `AI_HEARTBEAT` — `requestId`; every 20 s while the run is alive, resets the page's liveness watchdog (no UI change)
- `AI_RESULT` — `text`, `editable`, `displayMode`, `tooltipSettings`, `actionId`, `sourceText`, `conversation` (`[...messages, assistant]`, `null` for DeepL), plus `webhooks` (`[{id, name}]` — names only, no secrets) and `webhookData` (payload fields for a manual webhook send)
- `AI_ERROR` — `message`, `partialText`, `retry`, `tooltipSettings`
- `ASK_PROMPT` — `selectionText`, `tooltipSettings`; content shows the Ask input

Content → background (`chrome.runtime.sendMessage`):
- `SEND_WEBHOOK` — carries `webhookId` + `webhookData`; the background resolves the webhook from storage, renders its payload template, delivers it, and answers `{ok}` or `{ok: false, error}` via `sendResponse`
- `RUN_ACTION` — carries `actionId` + `selectionText` + `editable` (sent by the floating selection button); the background resolves the action from settings and calls the shared `runAction`
- `CANCEL_ACTION` — `requestId`; aborts the tab's run only if the id matches
- `RETRY_RUN` — `retry`, `clientId`
- `REFINE_ACTION` — `actionId`, `conversation`, `preset` or `instruction` (neither = Retry), `sourceText`, `clientId`
- `RUN_ASK` — `question`, `selectionText`, `clientId`

`sendToTab()` in `background.js` silently catches errors when the content script isn't loaded (restricted pages like `chrome://`).

### Refine and Ask

**Refine** — every LLM result tooltip (not DeepL, not explicit insert mode) has refine controls: a `Refine ▾` drop-up (`Shorter`, `Longer`, `Simpler`) at the left end of the Send/Copy row, and a `Follow up…` input above that row. The drop-ups (Refine, Send) close on any click outside them; with one open, a click on the page closes only the menu, not the tooltip (`closeActionMenus`). Successful results have no Retry button (Retry lives only in the error tooltip; `REFINE_ACTION` without `preset`/`instruction` still regenerates). Presets are sent as keys and resolved in the background via `REFINE_PRESETS` (`lib/chat.js`). The conversation travels with the tooltip (the worker may have restarted): `sanitizeConversation` requires user-first strict alternation ending in assistant, ≤ 100 000 chars per message, and trims to the first pair + last 18 (`MAX_CONVERSATION_MESSAGES` = 20). Config: `ASK_ACTION_ID` (`'__ask__'`) → `pickLLMConfig(configs)`; otherwise the action's config via `resolveActionConfig(configs, action)` (`lib/chat.js`, also used by `runAction`): the config with `modelConfigId`, `configs[0]` for an empty id, and `null` when a set id no longer exists → `"This action's model was removed — pick another in settings"` (no silent fallback to another model). Refine of a DeepL-backed action fails with "Refine is not available for DeepL".

**Ask** — "Ask about selection…" (context menu item `contexthelper-ask`, always present even with zero actions) and the `ask-selection` command (no suggested key). The background sends `ASK_PROMPT`; the content input captures the selection and anchor before focusing, stops key-event propagation, handles Esc locally and ignores Enter while `isComposing`. `RUN_ASK` builds `buildAskPrompt(question, text)` and runs on the first non-DeepL config.

**Inputs in the closed shadow root** — focus retargets `document.activeElement` to the host; use held element references. `stopPropagation` keeps bubble-phase page shortcuts (GitHub, Gmail) out, but capture-phase `window` listeners still see the keys.

### Key architectural rules

**Service worker listeners must be registered synchronously** — MV3 service workers can be terminated after ~5 min idle. Listeners registered inside `async` functions or after an `await` will be lost on revival. Always register `chrome.contextMenus.onClicked.addListener` and `chrome.commands.onCommand.addListener` at the top level.

**Content script must remain IIFE** — MV3 content scripts do not support `type: "module"`. Only `background.js` and `options.js` use ES module `import/export` (content.js cannot import `lib/` — keep shared logic message-driven, e.g. refine presets are resolved in the background).

**Shadow DOM isolation** — all UI (tooltip, spinner) lives inside a closed Shadow DOM attached to a host `div`. This prevents host page styles from leaking in. `content.css` resets the host element (`all: initial !important`), while internal styles are injected via `getShadowStyles()` into the shadow root. Keep both in sync — `content.css` protects against host-page interference, `getShadowStyles()` defines the actual component styles.

**Storage split** — `chrome.storage.local` holds `modelConfigs` (array of `{ id, name, provider, model, apiKey, effort, baseUrl? }` — `baseUrl` only for `custom`, stored normalized; `effort` is `'' | 'low' | 'medium' | 'high'`, `''` = provider default, always `''` for DeepL, sanitized on save and backfilled on read), `webhooks` (array of `{ id, name, url, method, headers, template }`) — both contain secrets and are not synced to Google account — and `modelListCache` (live model lists keyed `<provider>:<key fingerprint>`, `openrouter`, `custom:<baseUrl>[:<fingerprint>]` and `deepl-langs:<fingerprint>` — see Model lists below; no secrets, local-only cache). `chrome.storage.sync` holds `actions`, `tooltipSettings`, `floatingButtonSettings`, `systemPrompt`, `darkMode`. Actions reference model configs via `modelConfigId`; webhooks are a global list, not bound to actions (a legacy `webhookId` field on actions is stripped on read and write). All actions share the one `actions` sync item, so together they must fit Chrome's 8 KB per-item limit (UTF-8 bytes of key + JSON). `saveSettings` checks it before any write and fails with a readable error naming the longest prompts (`actionsQuotaError`); the options page shows a live meter under the list (`actionsSyncUsage`, orange above 85 %, red above 100 %). Splitting actions into per-key items was tried and parked (branch `parked/per-action-sync-keys`): multi-key writes are not atomic and keys sync separately, so concurrent saves, read-time migration and devices on an older version could lose actions without a single-writer/revision design.

**Migration** — `getSettings()` auto-migrates two legacy schemas: (1) old single-provider data (separate `provider`, `model`, `apiKey` fields) into a `modelConfigs` array on first access — idempotent via `modelConfigs === null` check, creates one config from old fields, assigns it to all actions, cleans up old keys. (2) Legacy boolean `darkMode` is mapped to the tri-state form: `true` → `'dark'`, `false` → `'auto'`. New installs default to `'auto'`, which follows `prefers-color-scheme` via `matchMedia` (re-applied on system theme change while in `'auto'`).

**Theme flash (FOUC) prevention** — `options.js` is an ES module, so it only applied the theme after parsing plus the async `getSettings()` read; the page painted light first. Two defenses now run before it:

1. `theme-boot.js` — a **classic, non-deferred** script in `<head>` — reads the mirrored preference from `localStorage` (`contexthelper.theme`) and sets `documentElement.dataset.theme` before any page content is parsed. It cannot be a module (implicitly deferred → runs after parse) and cannot be inline (MV3 CSP), so it duplicates `resolveTheme` from `lib/theme.js` — keep the two in sync. Head placement is load-bearing: an *external* script at the start of `<body>` still loses the race, because the parser blocks on its fetch after `<body>` is open and Chrome paints the light canvas meanwhile (measured).
2. `options.css` keys every dark rule off `html[data-theme="dark"]` — **not** a body class, since a head script has no `document.body`. It also sets `color-scheme` and the dark canvas background there, with a `prefers-color-scheme` media query on `html:not([data-theme])` covering the window before the boot script runs (a brief dark canvas for a light-preference user on a dark system is the accepted trade for killing the white flash).

The `localStorage` mirror is written only where the value is authoritative (after `getSettings()` in `init`, and after a successful `saveSettings` in `onSave`), never in `applyDarkMode`, so an unsaved theme cycle can't poison the next boot. A profile that receives an explicit `darkMode` through `chrome.storage.sync` from another device still flashes once on first open — the mirror is per-profile and has nothing to read yet.

**Text replacement** has three strategies in `content.js`:
- `replaceSelectedText()` — for editable inputs/textareas (native setter trick to bypass React synthetic events) and contenteditable (`document.execCommand('insertText')` to preserve undo stack)
- `forceReplaceInDOM()` — modifies read-only DOM via Selection API; only used when `displayMode === 'insert'`
- Tooltip fallback — when neither editable context is available

### Error handling pattern

`lib/api-client.js` uses a layered approach:
- `fetchWithErrorHandling()` — wraps `fetch` with AbortController timeout (90s) and maps network errors (AbortError → timeout, TypeError → no connection). For non-streaming calls it also reads the JSON body (`readJSONUntilAbort`) while the external abort and the 90 s deadline still apply, so a server that sends headers and then stalls can be cancelled or times out; streaming calls pass `skipBody` and hand the body to `readStream`.
- `safeParseJSON()` — catches non-JSON error bodies (e.g., 502 HTML pages) that would throw SyntaxError
- **Reasoning models** — thinking counts toward the output budget, so the budgets are large: Anthropic `ANTHROPIC_MAX_TOKENS` 16 000, Gemini `GEMINI_MAX_OUTPUT_TOKENS` 16 000, OpenAI `max_completion_tokens` `OPENAI_MAX_COMPLETION_TOKENS` 25 000; OpenRouter and custom keep `max_tokens` `MAX_TOKENS` 4096. `temperature` (0.3) goes only to OpenRouter and custom: `anthropic-version: 2026-10-21` rejects it, Gemini 3.6+ ignores it, GPT-6 rejects it. Anthropic never gets `thinking` (Claude 5.x is adaptive by default).
  - **Reasoning effort** — `callAI({ effort })` (`normalizeEffort`: `'low' | 'medium' | 'high'`, anything else sends nothing) maps to `output_config: { effort }` (Anthropic), `reasoning_effort` (OpenAI, custom), `reasoning: { effort }` (OpenRouter), `generationConfig.thinkingConfig.thinkingLevel` `LOW|MEDIUM|HIGH` (Gemini); DeepL ignores it. `runChat` and the options Test button pass `config.effort`.
  - **Per-field fallback** (`postWithTuningFallback`, used by Anthropic, Gemini and `callChatCompletions`) — a 400 (it arrives with the headers, before `readStream`) whose message names a tuning field **that is in the body** (`temperature`: `/temperature/i`; effort: `/effort|reasoning_effort|reasoning|thinking_?level|thinkingConfig|output_config/i`) is retried once without only that field — at most once per field, same `signal` / `onDelta`, abort checked between attempts. SSE errors are never retried. `${endpoint}|${model}|${field}` goes into `_rejectedTuning` (worker lifetime) only after the retry got an OK response; later calls drop the field up front. Gemini keys on `GEMINI_BASE_URL|model`, so the plain and the streaming endpoint share it.
  - **Empty answers** — `normalizeStopReason` maps every provider's raw stop reason to `length | refusal | stop | other`. An answer with no text (non-stream, or after the stream ended — EOF without a terminal event stays "stream ended unexpectedly") becomes: `length` (`max_tokens` / `length` / `MAX_TOKENS`) → "The model used its whole token budget on reasoning — lower Reasoning effort"; `refusal` (`refusal` — Anthropic sends it as HTTP 200 — `content_filter`, `SAFETY`, `PROHIBITED_CONTENT`, `BLOCKLIST`, `SPII`, also a blocked Gemini prompt) → "The model declined to answer". Both are `APIError` with `retryable: false` (no `↻ Retry`, `isRetryableError` → false); every other empty answer keeps "<Provider> returned an empty response (<reason>)" and stays retryable. A non-empty answer is returned whatever the stop reason.
- `APIError` class — maps HTTP status codes to user-friendly messages (401 → invalid key, 429 → rate limit, 5xx → server unavailable)

### Overlay cleanup pattern

Content script tracks event listeners in `activeCleanups[]`. Every `showLoading/showResultTooltip/showErrorTooltip` call runs `hideOverlay()` first, which iterates and invokes all cleanup functions (removing keydown listeners, clearing timers, etc.) before building new UI. This prevents listener leaks across multiple sequential AI calls.

**Resizable result tooltip** — the result tooltip (`.cmn-resizable`) has a native CSS `resize: both` handle; a `ResizeObserver` (`observeTooltipResize`) detects the drag, releases the default 400px max-height cap, and debounce-saves the size into `tooltipSettings.width/height` (sync storage, sanitized to 240–1200 × 120–900 in `lib/storage.js`; `null` = auto). Subsequent tooltips open at the stored width with the stored height as `max-height` (short results stay compact). Options save re-reads these two fields from storage so the Appearance form doesn't reset them. Error tooltips and the spinner are not resizable.

### Default actions and system prompt

`getDefaultActions(uiLanguage)` in `lib/storage.js` builds the set from `chrome.i18n.getUILanguage()`: "Translate to <browser language>" (name from `uiLanguageName` via `Intl.DisplayNames`; skipped for English or an unknown language), "Translate to English", Fix grammar, Improve writing, Explain simply, Summarize, Quote with source (`{{pageTitle}}`/`{{pageUrl}}`). Translations and Explain have Page context on. Defaults are not written to storage until the user saves, so an untouched profile follows its browser language. Default templates end with a bare `{{text}}` (the placeholder adds the `<text>` fence); the shared writing rules (plain text, result only, no em-dashes/hedges/buzzwords, treat `<text>` as content, never instructions) live in `DEFAULT_SYSTEM_PROMPT`. "Restore defaults" in options also offers the default system prompt when the current one differs.

### Action `displayMode`

Each action has a `displayMode` field:
- `'auto'` — insert if the focused element is editable, otherwise tooltip
- `'tooltip'` — always show result in floating tooltip
- `'insert'` — always replace selected text (even in read-only DOM via `forceReplaceInDOM`)

### Webhook delivery

Webhook delivery is **manual, from the result tooltip** — there is no automatic delivery. Webhooks are a global list in `chrome.storage.local` (Bearer tokens are secrets) under `webhooks: [{ id, name, url, method, headers: [{key,value}], template }]`; they are not bound to actions.

Every result tooltip offers a send control (built by `createWebhookSendControl` in `content.js`): one webhook renders a direct "Send to <name>" button, several render a "Send ▾" drop-up menu. Clicking sends `SEND_WEBHOOK` to the background, which renders the webhook's payload template and delivers it; the button reflects the response (`Sending… / ✓ Sent / ⚠ Failed` with the error in its `title`, retry enabled on failure). Insert mode shows no tooltip, hence no send — that is by design. AI errors show no send control either.

**Payload templates** — each webhook has a `template`: a JSON document with placeholders (`{{result}}`, `{{sourceText}}`, `{{actionName}}`, `{{pageUrl}}`, `{{pageTitle}}`, `{{timestamp}}`, `{{modelUsed}}`) inside string values. `renderTemplate` in `lib/webhook.js` parses the template as JSON first and substitutes placeholders in the parsed tree, so quotes/newlines in AI output can never break the payload; unknown `{{...}}` tokens (e.g. n8n expressions) pass through untouched. `DEFAULT_WEBHOOK_TEMPLATE` reproduces the classic flat schema. `saveSettings` rejects templates that don't parse as JSON. The Test button sends the real template rendered with sample data, so a passing test validates the actual payload shape.

Permissions are granted **per-origin at runtime** via `chrome.permissions.request` — a single combined prompt on Save (`requestWebhookPermissions`, called before any `await` to preserve the user gesture) and per-webhook on Test. The manifest declares `optional_host_permissions: ["http://*/*", "https://*/*"]` so users only grant access to the specific origins they configure (e.g. `https://api.notion.com/*`).

### Keyboard shortcuts

`chrome.commands` are static (declared in `manifest.json`) — Chrome does not allow per-action dynamic commands. The extension declares 4 fixed slots `run-action-1..4` (suggested defaults Ctrl+Shift+1..4; on macOS only slots 1–2 get suggestions since Cmd+Shift+3/4 are system screenshots). Each action has a `shortcutSlot: '' | '1'..'4'` field (sync storage); the options action card has a `.action-shortcut` select whose labels show the live key combos from `chrome.commands.getAll()`. Slot uniqueness: auto-steal in the options DOM (radio-like) + duplicate rejection in `saveSettings`.

Trigger path: `chrome.commands.onCommand → handleCommand` in `background.js` — maps the command to the action via `shortcutSlot`, reads the selection from the page with `getSelectionFromTab` (`probeSelection` via `chrome.scripting.executeScript`), then calls the shared `runAction`. A password/payment field holding the selection shows "ContextHelper does not send password or payment fields" (checked before the empty test, also for the Ask command). Empty selection shows a "Select some text first" tooltip (requires the `AI_PROCESSING_START` + `AI_ERROR` pair — content.js gates `AI_ERROR` on the requestId set by START). Restricted pages are a silent no-op. Context-menu titles append the current combo (e.g. "Translate to English (Ctrl+Shift+1)"), refreshed on every menu rebuild. Key combos themselves live in Chrome (`chrome://extensions/shortcuts`), not in extension storage — the options footer links there via `chrome.tabs.create` (plain anchors to chrome:// are blocked).

### Floating selection button

A third trigger path besides the context menu and keyboard shortcuts: select text → after `delayMs` an emoji pill fades in near the end of the selection → hover expands the pinned action's name → click sends `RUN_ACTION` to the background, which runs the standard `runAction` flow.

**Per-domain opt-in** — the feature requires a content script present *before* any action runs, but the extension must not demand all-sites access. The page context menu ("Floating button: enable/disable on this domain", shown on `page` + `selection` contexts) requests the host permission for that single domain (`chrome.permissions.request` inside the click gesture) and toggles the hostname in `floatingButtonSettings.domains`. On toggle-on the background also injects `content.js` into the current tab directly (`ensureContentScript`) — the registered script only covers future navigations, and this makes the button work without a refresh. `syncFloatingButtonRegistration()` in `background.js` keeps a dynamically registered content script (`chrome.scripting.registerContentScripts`, id `contexthelper-floating`, `persistAcrossSessions`) in step with that list — called from `storage.onChanged`, `onInstalled` and `onStartup` (self-healing; skips origins whose grant was revoked). Empty list + `allSites: false` = script unregistered, zero footprint.

**All-sites toggle** — the options card also offers `allSites`: enabling requests the broad `http://*/*` + `https://*/*` grant within the Save click gesture (denied → toggle reverts); disabling removes the broad grant and re-registers for the domain list only. Already-loaded tabs stop showing the button immediately via `storage.onChanged` in the content script, though the injected script itself lives until reload.

**Permission-subtraction pitfall** — `chrome.permissions.remove` subtracts everything the removed pattern *contains* from the active permission set. Removing `https://*/*` therefore also strips the **required** API `host_permissions` from the manifest (all https), and every AI fetch starts failing CORS ("No internet connection" in the tooltip). The subtraction also strips the per-domain opt-in grants. Defenses in the code: (1) `onSave` in `options.js` re-requests the manifest `host_permissions` **plus** every listed domain, every webhook origin and every custom-endpoint origin (`buildRestoreOrigins` in `lib/webhook.js`; a refused re-request shows "some permissions could not be restored — click Save again") (read from the rendered chips — a storage read would forfeit the gesture) inside the same click gesture on **every** save — one combined prompt at most, silent when everything is still granted — which both pairs with the untoggle removal and self-heals already-affected profiles; (2) per-domain removals (`removeFloatingDomain` in options, the context-menu toggle in background) skip `permissions.remove` when the host is covered by a manifest pattern, used by a webhook, or used by a custom model endpoint; (3) `background.js` re-runs `syncFloatingButtonRegistration` on `chrome.permissions.onAdded/onRemoved`, because the re-grant can land after the `storage.onChanged` resync already filtered the domain out. Never remove a broad origin pattern without re-requesting the manifest hosts in the same gesture.

**Appearance rules** (content.js) — button shows only for selections of ≥3 chars outside editable contexts (input/textarea/contenteditable); `selectionchange` + `mouseup` re-arm a `delayMs` timer, so it appears once the selection is stable. Hides on: deselect, outside mousedown, Esc, scroll, and `AI_PROCESSING_START`. The button element (`.cmn-float-btn`) deliberately lacks the `.cmn-overlay` class and has its own cleanup list (`floatingCleanups`) — `hideOverlay()` must not remove it, and vice versa. `floatingButtonSettings` (`{ delayMs, actionId, emoji, bgColor, domains, allSites }`, sync storage, sanitized in `lib/storage.js`) is read at injection and refreshed live via `storage.onChanged`. A non-default `bgColor` is applied inline (which also disables the CSS hover lightening); dark backgrounds get an auto-contrast light label/border.

### Options page tabs

`options.html` is organized into 4 tabs (`Models | Webhooks | Appearance | Actions`). Each tab is a `<div class="tab-panel" data-tab="...">`; the System prompt sits inside the Actions tab as a separate card. `initTabs()` in `options.js` toggles `.active` and the `hidden` attribute on click. To add another tab: drop a `<button class="tab-btn" data-tab="X">` in the nav and a matching `<div class="tab-panel" data-tab="X" hidden>` in `<main>` — no JS change needed.

**`[hidden]` pitfall** — any element whose class sets `display:` (e.g. `.field-hint`, `.emoji-picker`) silently defeats the UA's `[hidden] { display: none }` rule, so `el.hidden = true` does nothing. Every such class needs an explicit `.the-class[hidden] { display: none }` override in `options.css` (bitten twice: emoji picker, model warning hint). The same pitfall applies to the shadow styles in `content.js` (`getShadowStyles()`) — bitten there too: the webhook send menu (`.cmn-send-menu`).

### Adding a new AI provider

1. Add provider ID to `VALID_PROVIDERS` in `lib/storage.js`
2. Add URL constant + `callXxx()` function in `lib/api-client.js` — map `effort` (through `postWithTuningFallback`) and add the provider's raw stop reasons to `normalizeStopReason`
3. Add branch in `callAI()` in `lib/api-client.js`
4. Add fallback model list to `getAvailableModels()` and default model to `DEFAULT_MODELS` in `lib/api-client.js`
5. Add a live-list branch in `fetchAvailableModels()` in `lib/api-client.js` (skip if the provider has no models endpoint — the static list then stays)
6. Add `<option>` to provider `<select>` in `modelConfigTemplate` in `options.html`
7. Add host permission in `manifest.json`

**OpenAI-compatible endpoints need no new provider** — the `custom` provider covers them: user-supplied `baseUrl` (`normalizeBaseUrl` strips a trailing `/` or `/chat/completions`; plain `http` only for local and private-network hosts per `isPrivateHost` — localhost, `*.local`, `*.internal`, `*.lan`, `*.home.arpa`, single-label names like `gpu-box`, 127/8, 10/8, 172.16/12, 192.168/16, 100.64/10 (Tailscale/CGNAT) and 169.254/16; IPv6 literals rejected because Chrome match patterns don't cover them), optional API key (`Authorization` only when set), models from `${base}/models`. Its origin is not in `host_permissions`: the options page requests it per origin (`customOrigins` in `lib/storage.js`) on Test and on Save. A 403 is remapped to an Ollama hint (`OLLAMA_ORIGINS=chrome-extension://*`).

### Model lists (live + fallback)

The model combobox in options is **stale-while-revalidate** over three layers, in order: the static fallback in `getAvailableModels()` (instant), the cached live list from `modelListCache` in `chrome.storage.local`, and a live `fetchAvailableModels(provider, apiKey, signal, baseUrl)`. The live fetch always runs once per cache key per page session (`liveFetchedModelLists` in `options.js`); `forceFetch` refetches — the `↻` button next to the field, a key/base-URL edit (600 ms debounce) and a successful Test. The 24 h TTL only changes the hint text ("cached, may be outdated").

- **Cache keys** (`modelCacheKey` in `lib/model-list.js`): `<provider>:<fingerprint>` for anthropic/openai/google — a key may see its own models; the fingerprint (`keyFingerprint`) is the first 12 hex chars of SHA-256(apiKey), so the key is never stored — `openrouter` (public list) and `custom:<normalized baseUrl>` (keyless) or `custom:<normalized baseUrl>:<fingerprint>` (with a key); a cache key names the whole list identity, so it is also the session-dedup key; `deepl-langs:<fingerprint>` holds a DeepL key's target languages (see DeepL below). Every write goes through `updateModelListCache(mutator)` in `lib/storage.js`: one module-level promise chain serializes the read-modify-write cycles (concurrent cards never drop each other's entries), and each write prunes entries not refreshed for 7 days (old fingerprints, removed endpoints, legacy per-provider keys). `setCachedModelList(key, models, { startedAt })` stores the fetch's start stamp (strictly increasing per page, `nextModelFetchStamp`) with the page's `MODEL_FETCH_SESSION_ID` (`crypto.randomUUID()`) and resolves `false` without writing when the stored entry comes from the same session and its fetch started later (another session's entry is always replaced — stamps of different pages are not comparable); a `fetchedAt` in the future reads as stale and is pruned — an older request that finished last never overwrites a newer list; a key joins `liveFetchedModelLists` only once its list was stored.
- **Warning** — each card keeps `listState = { seq, source, verified }`. `source` is `'builtin' | 'cache' | 'live'`; `shouldWarnUnknownModel(value, ids, source, verified)` (`lib/model-list.js`) warns only for `cache`/`live`, never against the dated built-in list, and never for the exact `provider|key|baseUrl|model` tuple a successful Test confirmed (`markVerified`, which ignores a Test that finished after the card changed). Text: `⚠ "X" is not on the list returned by <Provider> — check the ID`. A model missing from the live list still warns — only listed or Test-confirmed IDs are silent. Validation runs on `change`, not mid-typing.
- **Race guards** — every `populateModelDatalist` run takes a new `listState.seq`; provider, key and base-URL edits (including a switch to DeepL) bump it synchronously through `invalidateModelList`, which also resets `source` to `'builtin'`, clears `verified`, hides the warning and the Test result, and re-renders the built-in list (custom: the placeholder) at once via `refreshModels(false, { renderOnly: true })` — the old key's list is never offered during the 600 ms debounce. Test snapshots provider/key/baseUrl/model/effort before any await, uses the snapshot for the request and `markVerified`, and renders its result (success, error, DeepL usage, denied permission) only while the card still shows the tested identity and effort (`testTuple`; an effort change hides the result). The run captures provider/key/baseUrl as values, renders the built-in list before hashing the key, and re-checks `seq` after every await; a superseded run never touches the list, the hint or `source` (it still caches its list under its own key).
- **Failures** are no longer silent: the hint says "Built-in list — couldn't load the live list" (custom: "Couldn't load the endpoint's model list — type the model ID"; with a cache showing: "N models · cached — couldn't refresh") with the error message in the hint's `title`.

Per-provider notes (`fetchAvailableModels` in `lib/api-client.js`; filters are internal, tested through it with stubbed `fetch` in `tests/model-lists.test.js`): Anthropic `limit=1000` + `after_id`/`has_more`, Gemini `pageSize=1000` + `pageToken`, both capped at `MODEL_LIST_MAX_PAGES` (5) and stopped early when any cursor repeats, ids deduplicated; Anthropic drops `lifecycle` `deprecated`/`retired`; OpenAI keeps `OPENAI_CHAT_MODEL_RE` (`gpt-<digit>`, `o<digit>`, `chatgpt-`, `chat-latest`) minus `OPENAI_NON_CHAT_RE` (embedding/audio/image/realtime and Responses-only models such as `-pro`, `codex`, `deep-research`); Gemini keeps `generateContent` models minus `GEMINI_NON_TEXT_RE` (image, tts, embedding, live, veo, …) and strips the `models/` prefix; OpenRouter's list is public (no key needed, ~400 entries, hence the autocomplete combobox instead of a `<select>`), minus `:batch` entries and models whose `architecture.output_modalities` lacks `text`; DeepL has none. Static `DEFAULT_MODELS` rot over time — a prefill that is still auto-filled (never touched by the user, tracked via `modelAutoFilled`) and missing from a freshly loaded list is auto-replaced with the closest live ID (`closestModelId`: longest common prefix, ties broken by shared name tokens); saved/user-typed values are never rewritten, since retired models often keep working for existing keys.

### DeepL (non-LLM provider)

DeepL is a translation API, not a chat LLM, so it deviates from the checklist above:
- **No model** — the Model field is hidden in the config card (`syncProviderFields` in `options.js`), `model` is stored as `''`, and `saveSettings` skips the model requirement for `provider === 'deepl'`.
- **Per-action `targetLang`** instead of a template — when an action's selected config is DeepL, `syncActionCardMode` in `options.js` hides the template textarea (kept in the DOM so its value survives switching configs) and shows a target-language `<select>`. Plain `EN`/`PT` are deprecated by DeepL — use regional variants (`EN-US`, `PT-BR`).
- **Dynamic target languages** — `fetchDeepLTargetLanguages(apiKey)` (`lib/api-client.js`) calls `GET /v3/languages?resource=translate_text`, keeps `usable_as_target`, and maps the BCP-47 codes (`en-US`, `zh-Hant`) to `{ id: CODE_UPPER, name }` (the shape of `DEEPL_TARGET_LANGUAGES`, matching stored `targetLang` values), deduplicated and sorted by name; only a v3 404 falls back to the deprecated `/v2/languages?type=target`. In `options.js` the select renders `DEEPL_TARGET_LANGUAGES` at once, then the cached list (`modelListCache` key `deepl-langs:<fingerprint>`, `deeplLangsCacheKey` in `lib/model-list.js`, written through `setCachedModelList` with the page's session id and fetch stamp), then the live one. The race rules live DOM-free in `lib/deepl-languages.js` (tested with deferred promises): `createDeepLLanguageLoader` loads once per key per page, shared by every action card on that key, and drops a failed **or empty** load so the key can be fetched again — but remembers the failure time per key and, for `FAILURE_COOLDOWN_MS` (30 s), answers routine requests for that key with the cached list only and no request (a key that keeps failing, e.g. 403, is not refetched on every config-name keystroke via `refreshActionModelSelectors`); only explicit retries pass `force` — the key-edit debounce and a successful DeepL Test, through `syncAllActionCardModes(forceKey)`, for cards on that key; `syncTargetLangState` (called from `syncActionCardMode`) reloads only when the card's DeepL key changed (per-card `identity` + `seq` in `targetLangStates`; a superseded load never renders, a cached list never replaces a live one, and a failed/empty load resets `identity`, so the next sync — action config switch, provider toggle, key edit, successful DeepL Test — retries); `invalidateTargetLangState` bumps `seq` and clears `identity`. A DeepL key keystroke invalidates the cards on that config **synchronously** (`invalidateDeepLActionCards`, built-in list shown) so the old key's in-flight load cannot render during the 600 ms debounce, after which `syncAllActionCardModes` loads the new key; a card switched to a non-DeepL config is invalidated too (switching back reuses a finished load). After a successful Save each card's `saved` value comes from the persisted `actions` snapshot (by action id). Every render goes through `targetLangOptions` (pure, `lib/model-list.js`): ids upper-cased, the saved and the currently selected value always kept as options (no data loss for a language missing from the list), a lowercase saved code normalized. `saveSettings` only requires a non-empty `targetLang` — no format or list check.
- **Endpoint auto-detection** — `getDeepLBaseUrl(apiKey)` picks `api-free.deepl.com` when the key ends with `:fx`, otherwise `api.deepl.com`. Both origins are in `host_permissions`.
- **No system prompt, no template substitution** — `background.js` sends the raw selection; `callAI` routes to `callDeepL` before any model resolution.
- **Test button** calls `GET /v2/usage` (via `getDeepLUsage`) instead of a chat call, and shows the character quota.
- **Error mapping** — DeepL returns 403 for bad keys (remapped to 401 for the shared message) and 456 when the character quota is exhausted (mapped in `APIError`).

### Action template syntax

Templates must contain `{{text}}` as the placeholder for selected text. It always expands to the selection fenced as `<text>\n…\n</text>` (`fenceText` in `lib/prompt.js`; Ask uses it too), which `DEFAULT_SYSTEM_PROMPT` tells the model to treat as content, never instructions; a hand-written `<text>` fence around `{{text}}` in older templates is removed on read and save (`unwrapTextFence`) so it is never nested. Optional placeholders: `{{pageTitle}}`, `{{pageUrl}}` (listed with click-to-copy chips in the collapsible "Template placeholders" box of the Actions card). `renderActionPrompt` in `lib/prompt.js` replaces them in **one pass** with a function replacer, so selected text containing `{{pageUrl}}` or `$&` is inserted literally; unknown `{{x}}` tokens stay. **Page context** is a per-action checkbox (`includePageContext`, boolean in sync storage): `buildActionPrompt` appends a `<page_context>` block (page title, URL and the surrounding text) plus a "background only" note after the rendered template; `defuseFenceTags` swaps the `<` of any tag named `text`/`page_context` (any case, with attributes, `/`, whitespace or invisible format characters; not `<textarea>`/`<texts>`) inside the selection or page data for `‹`, so neither the default templates' `<text>` fence nor the page block can be closed from page content. Ask fences the selection the same way (`buildAskPrompt`). Sibling blocks use `innerText` (rendered text only, nothing hidden). The surrounding text is the selection's paragraph or text-control value; a paragraph or list item under 600 chars also takes in its visible sibling `p`/`li`/`blockquote`/`dd` blocks, nearest first, until ~1500 chars, never past a heading (`probeSelection`); whitespace is then collapsed with paragraph breaks kept (`collapseWhitespace`) and the result windowed to 2000 chars around the selection (`windowAround`). `{{context}}` used to be a placeholder: `migrateContextPlaceholder` (in `getSettings` and `saveSettings`) strips it from actions saved before the checkbox existed — those without an `includePageContext` field — and turns the checkbox on; it runs once, so a `{{context}}` typed later stays as plain text. `getPageContext` runs only when the checkbox is on or the template uses `{{pageTitle}}`/`{{pageUrl}}` (`templateUsesPageVars`), and reads the top frame only. Ask about selection never reads the page. A retry reuses the first run's `pageVars`. Exception: actions backed by a DeepL config bypass the template entirely (validation requires `targetLang` instead).

### Selection probe and sensitive fields

`probeSelection(rules, withContext)` in `lib/page-probe.js` is the **only** function injected to read a selection (`getSelectionFromTab`, `getPageContext`, and the context-menu check, via `runSelectionProbe`). `chrome.scripting.executeScript({ func: probeSelection, args: [SELECTION_RULES, withContext] })` serializes it, so it **must stay self-contained** — parameters and page globals only, no module references (the test suite runs it rebuilt from its source to enforce this). `SELECTION_RULES` holds the rule as data: text input types (text/search/url/email/tel) and the case-insensitive `autocomplete` pattern (`password` or a `cc-` token). The probe follows focus into open shadow roots, decides sensitivity from attributes only (`type=password` or the `autocomplete` pattern) and never reads such a field's `.value`. A sensitive field blocks (`sensitive: true`, no text) only when it holds the selection — `selectionEnd > selectionStart` (guarded read), or offsets unreadable and `window.getSelection()` empty; a sensitive field that is merely focused falls through to the page selection. The probe returns `{ text, editable, sensitive, inspected, blockText, start, end, title, url }`, and lets non-text controls (checkbox, range, button) fall through to `window.getSelection()`.

Context-menu clicks with `info.editable` (actions and Ask) probe the focused field in the clicked frame (`frameIds: [info.frameId ?? 0]`) before using `info.selectionText`; a sensitive field, **a frame that cannot be probed, or a probe that did not reach the editable element** (`inspected: false` — the resolved focus is not an input/textarea or contenteditable, e.g. the host of a closed shadow root) fails closed with "ContextHelper does not send password or payment fields". The keyboard path does not use `inspected`: it reads the selection itself, and Chromium masks a password selected inside a closed shadow root as `•••` in `window.getSelection()`.

**Known limitation:** frames are not otherwise propagated — runs, insertion and page context target the top frame. An editable selection in a cross-origin iframe the extension cannot script gets the sensitive-field notice instead of running; so does an editable selection inside a closed shadow root (the menu path cannot inspect it).
